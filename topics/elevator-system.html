Elevator System

Multi-elevator dispatch, worked end-to-end — where the State and Strategy patterns stop being theoretical and start solving a real coordination problem.

🛗 Practice Problem ⏱ ~25 min read 🎯 State + Strategy in one design
💡 Why this problem is a step up from Parking Lot

Parking Lot is mostly about matching and composition. Elevator System adds a genuinely new dimension: coordination over time — each elevator has its own state machine, and a controller must decide which of several moving elevators should answer a new request. This is the problem that separates "I know the patterns" from "I can apply them under a real constraint."

1Problem Statement

Design an elevator system for a building with N elevators and M floors that supports:

  • Hall calls — a person on a floor presses "up" or "down" to request an elevator.
  • Car calls — a person inside an elevator presses a destination floor button.
  • A dispatch mechanism that decides which elevator answers a given hall call.
  • Each elevator moves toward its pending stops one floor at a time, opening its doors at each stop.

2Clarifying Requirements

Dispatch the "best" elevator for a hall callMinimize average wait time across all requests
Track each elevator's current floor, direction, and pending stopsHandle concurrent requests from multiple floors safely
Support both hall calls (external) and destination selection (internal)Dispatch algorithm should be swappable (nearest-car vs zoning) without touching the controller
Open doors automatically when an elevator reaches a requested floorScale from a small building (2 elevators) to a skyscraper (dozens) with the same core design

5Implementation

Enums & requests

python
from enum import Enum

class Direction(Enum):
    UP = 1
    DOWN = -1
    IDLE = 0

class ElevatorState(Enum):
    IDLE = "idle"
    MOVING = "moving"
    DOORS_OPEN = "doors_open"

class Request:
    def __init__(self, floor: int, direction: Direction = None):
        self.floor = floor
        self.direction = direction   # None for an internal car call (just a destination)

Elevator — a small state machine

python
class Elevator:
    def __init__(self, elevator_id: int, capacity: int = 8):
        self.id = elevator_id
        self.current_floor = 0
        self.direction = Direction.IDLE
        self.state = ElevatorState.IDLE
        self.capacity = capacity
        self.stops: set[int] = set()          # floors this elevator must still visit

    def add_stop(self, floor: int):
        self.stops.add(floor)
        if self.state == ElevatorState.IDLE:
            self.direction = Direction.UP if floor > self.current_floor else Direction.DOWN

    def step(self):
        """Advance the elevator by one simulated time unit."""
        if not self.stops:
            self.state = ElevatorState.IDLE
            self.direction = Direction.IDLE
            return

        if self.current_floor in self.stops:
            self.state = ElevatorState.DOORS_OPEN
            self.stops.remove(self.current_floor)
            print(f"Elevator {self.id}: doors open at floor {self.current_floor}")
            return

        self.state = ElevatorState.MOVING
        self.current_floor += self.direction.value
        print(f"Elevator {self.id}: moving to floor {self.current_floor}")
⚠️ This is a simplified state machine

Real elevator logic keeps moving in its current direction until no more stops lie ahead in that direction, then reverses (the "SCAN"/"LOOK" disk-scheduling algorithm) — it doesn't reset direction after every single stop. The version above is intentionally simplified for clarity; see the interview questions below for the production version of this idea.

Dispatch strategy

python
from abc import ABC, abstractmethod

class DispatchStrategy(ABC):
    @abstractmethod
    def select_elevator(self, elevators: list[Elevator], request: Request) -> Elevator:
        pass

class NearestElevatorStrategy(DispatchStrategy):
    def select_elevator(self, elevators, request):
        return min(elevators, key=lambda e: abs(e.current_floor - request.floor))

ElevatorController (Singleton)

python
class ElevatorController:
    _instance = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self, num_elevators: int = 4, strategy: DispatchStrategy = None):
        if getattr(self, "_initialized", False):
            return
        self.elevators = [Elevator(i) for i in range(num_elevators)]
        self.strategy = strategy or NearestElevatorStrategy()
        self._initialized = True

    def request_elevator(self, floor: int, direction: Direction) -> Elevator:
        """A hall call from a floor."""
        request = Request(floor, direction)
        elevator = self.strategy.select_elevator(self.elevators, request)
        elevator.add_stop(floor)
        print(f"Dispatched elevator {elevator.id} to floor {floor}")
        return elevator

    def select_floor(self, elevator_id: int, floor: int):
        """A car call from inside a specific elevator."""
        self.elevators[elevator_id].add_stop(floor)

Putting it together

python
controller = ElevatorController(num_elevators=3)

controller.request_elevator(floor=5, direction=Direction.UP)   # a hall call
controller.select_floor(elevator_id=0, floor=8)                 # a car call inside elevator 0

for _ in range(6):
    for elevator in controller.elevators:
        elevator.step()

same_controller = ElevatorController()   # Singleton -> same instance, same elevators
print(controller is same_controller)     # True

6. Extending the Design (common follow-ups)

🎤 "Your dispatch algorithm looks naive — how would you improve it?"

Prefer an elevator that's idle or already moving toward the request in the same direction over one that's simply geographically nearest but moving away — otherwise you dispatch an elevator that has to overshoot, reverse, and come back, which is slower than picking a farther elevator already headed the right way. This is exactly why dispatch logic is a separate DispatchStrategy — you can swap in this smarter rule as a new class.

🎤 "How would real elevators avoid constantly reversing direction?"

The SCAN/LOOK algorithm (borrowed from disk-arm scheduling): an elevator keeps moving in its current direction, serving every pending stop along the way, and only reverses once there are no more requests ahead of it in that direction. This avoids the inefficient back-and-forth a naive "always answer the newest request" approach would cause.

🎤 "How would you add a capacity limit or an emergency/fire override?"

Capacity: track current load in Elevator and reject/skip it in DispatchStrategy once full. Emergency override: this is a great fit for Chain of Responsibility or a simple priority flag — an emergency request should bypass normal dispatch and force all elevators to a ground-floor "recall" state, which is naturally modeled as a distinct ElevatorState.

🎤 "How would you handle concurrent hall calls from multiple floors at once?"

Same concern as the Parking Lot's concurrent entry gates — wrap request_elevator in a lock so two simultaneous calls can't both select and reserve the same elevator based on stale state. For higher throughput, a per-elevator lock (rather than one global lock) reduces contention.

📌 Quick Revision — Cheat Sheet

  • Entities: Elevator, Direction/ElevatorState (enums), Request, DispatchStrategy, ElevatorController.
  • State: each Elevator tracks its own idle/moving/doors-open state and reacts accordingly on step().
  • Strategy: DispatchStrategy decides which elevator answers a hall call — swappable without touching the controller.
  • Singleton: one ElevatorController for the whole building.
  • Naive "nearest floor" dispatch is a good starting answer — but naming SCAN/LOOK as the production-grade follow-up is what separates a strong answer from a great one.
  • Concurrency, capacity limits, and emergency override are the three follow-ups interviewers reach for most often — have a one-sentence answer ready for each.
