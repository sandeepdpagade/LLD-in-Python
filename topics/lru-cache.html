LRU Cache

The classic "machine coding" LLD question — a pure data-structure design where the only requirement that matters is the Big-O.

⚡ Practice Problem ⏱ ~15 min read 🎯 O(1) get and put, from scratch
💡 Why this problem is different from the others

Every other problem on this page is about modeling real-world entities. This one is about picking the right data structure combination. A cache needs fast lookup by key (→ hash map) and fast reordering by recency (→ doubly linked list) — neither one alone gives you O(1) for both operations.

1Problem Statement

Design a fixed-capacity cache supporting:

  • get(key) — return the value, or -1 if not present, in O(1).
  • put(key, value) — insert or update a value in O(1).
  • When capacity is exceeded, evict the Least Recently Used entry automatically.

2Design Decisions

NeedData structureWhy
O(1) lookup by keyHash map (dict)Standard O(1) average-case key lookup
O(1) "move to most-recently-used"Doubly linked listRemoving/re-inserting a node needs only pointer updates — no shifting, unlike an array/list
O(1) eviction of the least-recently-used entryTail of the same linked listThe list is kept ordered by recency, so "least recent" is always exactly the tail
Avoid null-checks at the list's boundariesDummy head + tail sentinel nodesEvery real node always has a valid prev/next to link against — no edge cases for "list is empty" or "removing the only node"

3Implementation (from scratch)

python
class Node:
    def __init__(self, key=None, value=None):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache: dict = {}          # key -> Node, gives O(1) lookup

        self.head = Node()             # dummy head = most-recently-used side
        self.tail = Node()             # dummy tail = least-recently-used side
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node: Node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_to_front(self, node: Node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)
        self._add_to_front(node)       # touching a key marks it most-recently-used
        return node.value

    def put(self, key, value):
        if key in self.cache:
            self._remove(self.cache[key])

        node = Node(key, value)
        self.cache[key] = node
        self._add_to_front(node)

        if len(self.cache) > self.capacity:
            lru = self.tail.prev        # the real node right before the dummy tail
            self._remove(lru)
            del self.cache[lru.key]

cache = LRUCache(2)
cache.put(1, "A")
cache.put(2, "B")
cache.get(1)            # "A" -> 1 is now most recently used
cache.put(3, "C")       # over capacity -> evicts 2 (least recently used)

print(cache.get(2))     # -1 -> evicted
print(cache.get(3))     # "C"
🎤 Say this out loud before coding

"I need O(1) lookup and O(1) reordering, so I'll combine a hash map with a doubly linked list — the map gives me the node instantly, the list keeps them ordered by recency, and dummy head/tail sentinels let me avoid special-casing the empty-list or single-node cases." Stating this before writing code is worth more than the code itself.

💡 The Python shortcut worth mentioning

collections.OrderedDict already maintains insertion/access order and supports moving a key to the end in O(1) — it implements almost exactly this structure internally. Showing you know both the from-scratch version and this shortcut is a strong signal in an interview.

python
from collections import OrderedDict

class LRUCacheSimple:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = OrderedDict()

    def get(self, key):
        if key not in self.cache:
            return -1
        self.cache.move_to_end(key)     # mark as most recently used
        return self.cache[key]

    def put(self, key, value):
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)   # evict the least recently used (front)

4. Extending the Design (common follow-ups)

🎤 "How would you make this thread-safe?"

Wrap get and put bodies in a single threading.Lock — because both operations mutate the linked list and the map together, a per-operation (not per-node) lock is needed to keep the two structures consistent with each other.

🎤 "How would you add TTL-based expiry on top of LRU?"

Store an expires_at timestamp on each Node; in get, check it and treat an expired entry as a miss (evicting it lazily), or run a periodic background sweep for proactive cleanup — the same "lazy vs. active expiry" trade-off that real caching systems (Redis, etc.) make.

🎤 "What if you needed LFU (Least Frequently Used) instead of LRU?"

A genuinely different data structure: track an access-frequency count per key, and evict the lowest-frequency entry (ties broken by recency). This needs a frequency-to-keys map alongside the key-to-node map — a good way to show you understand LRU isn't "the" caching algorithm, just the most common one.

📌 Quick Revision — Cheat Sheet

  • Structure: hash map (key → node) + doubly linked list (ordered by recency).
  • get: look up in the map, then move the node to the front (most recently used).
  • put: insert/update at the front; if over capacity, evict the node at the tail.
  • Dummy head/tail sentinels eliminate empty-list and single-node edge cases entirely.
  • collections.OrderedDict gives you the same behavior in ~10 lines — know both versions.
