UML Basics

The minimum UML you actually need for LLD interviews — class diagrams, relationships, and sequence diagrams — with worked examples.

📐 Fundamentals ⏱ ~20 min read 🎯 Asked in almost every round
💡 Why this matters

You will rarely be asked to draw a "textbook perfect" UML diagram in an interview. But you're constantly expected to talk in UML terms — "Library composes Book copies", "Member is-a Person", "0..* multiplicity" — and to sketch a rough class diagram on a whiteboard/doc before writing code. This page is the 20% of UML that covers 95% of interview usage.

1. What is UML?

UML (Unified Modeling Language) is a standardized set of diagram types for visualizing the design of a system — its classes, their relationships, and how objects interact over time. In LLD interviews it's the shared vocabulary you use to communicate a design before (or while) writing code.

UML diagrams fall into two broad families:

FamilyAnswersCommon diagrams
StructuralWhat does the system look like?Class, Object, Component, Deployment
BehavioralHow does the system behave/interact?Sequence, Activity, State, Use Case
🎤 Interview reality check

Out of all UML diagrams, interviewers care almost exclusively about two: the Class Diagram (structure — your classes and how they relate) and the Sequence Diagram (behavior — how a specific use case flows across those classes). Master those two and you're covered.

2. Class Diagram Notation

Every class is drawn as a box with up to three compartments: name, attributes, and methods.

Class box anatomy: name / attributes / methods, each attribute or method prefixed by a visibility symbol

SymbolVisibilityPython equivalent
+Publicself.name
-Privateself.__name
#Protectedself._name
~Package/internalmodule-level convention
  • An abstract class name is written in italics (or tagged «abstract»).
  • An interface is tagged with the stereotype «interface» above the name.
  • A static member is underlined.
  • Method signatures follow name(param: Type): ReturnType.

3. Relationships Cheat Sheet

This is the single most interview-relevant part of UML — and the part everyone mixes up. Study the notation once, carefully.

NotationRelationshipMeaning
Association General "uses-a" relationship. Solid line, optional open arrow for navigability. E.g. Order ↔ Customer.
Aggregation "Has-a", weak ownership — the part can outlive the whole. Hollow diamond at the whole end. E.g. Library ◇— Member.
Composition "Has-a", strong ownership — part's lifecycle is tied to the whole. Filled diamond. E.g. House ♦— Room.
Inheritance
(Generalization)		 "Is-a". Solid line, hollow triangle pointing at the parent. E.g. Member ▷— Person.
Realization
(Implementation)		 Dashed line, hollow triangle. A class implements an interface/ABC. E.g. CreditCard implements PaymentMethod.
Dependency Weak, temporary "uses" — e.g. a parameter or local variable. Dashed line, open arrow. E.g. OrderService ⇢ Logger.

How each notation typically shows up in actual Python code:

python
class Engine: pass
class Logger: pass

class Car:
    def __init__(self, engine: Engine):
        self.engine = engine          # Composition -> Car owns Engine's lifecycle

class Garage:
    def __init__(self):
        self.cars = []                 # Aggregation -> cars can exist without the garage

    def park(self, car: Car):
        self.cars.append(car)

class Driver:
    def drive(self, car: Car):         # Association -> Driver "uses" Car (holds no ref)
        pass

class ReportGenerator:
    def generate(self, logger: Logger):  # Dependency -> only used inside this one method
        logger.write("report generated")

class ElectricCar(Car):                # Inheritance -> ElectricCar IS-A Car
    pass
🚨 #1 most-confused pair: Aggregation vs Composition

Ask yourself: "If the whole is destroyed, does the part die too?"

  • Composition: House and Room — delete the house, the rooms cease to exist. Strong, exclusive ownership.
  • Aggregation: Library and Member — close the library, the members (people) still exist independently.

In Python code, both often just look like self.rooms = [Room(...)] — the difference is conceptual ownership, not syntax. This is one of the most common interview verbal questions.

4. Multiplicity Notation

Multiplicity specifies how many instances of one class relate to instances of another — written near each end of a relationship line.

NotationMeaning
1Exactly one
0..1Zero or one (optional)
0..* or *Zero or many
1..*One or many (at least one)
3Exactly 3
2..4Between 2 and 4

Example: Library "1" o-- "0..*" Member reads as "one Library aggregates zero or more Members."

python
class Library:
    def __init__(self):
        self.address: str = None       # multiplicity 1   -> a single value
        self.manager: "Person" = None  # multiplicity 0..1 -> single value, can be None
        self.members: list = []        # multiplicity 0..* -> a collection
        self.founders: list = []       # multiplicity 1..* -> a collection, validated non-empty

    def add_founder(self, person):
        self.founders.append(person)   # must enforce "at least one" in code yourself

5. Worked Example: Library Management

A small class diagram combining inheritance, composition, aggregation, and association in one picture:

Member and Librarian(not shown) inherit Person · Library composes Book · Library aggregates Member · Member borrows Book

python
from abc import ABC, abstractmethod

class Person(ABC):
    def __init__(self, name, person_id):
        self._name = name
        self._person_id = person_id

    @abstractmethod
    def get_details(self):
        pass

class Member(Person):
    def __init__(self, name, person_id):
        super().__init__(name, person_id)
        self.__member_id = person_id
        self.borrowed_books = []          # association -> Book

    def get_details(self):
        return f"Member: {self._name}"

    def borrow_book(self, book):
        self.borrowed_books.append(book)

class Book:
    def __init__(self, title, isbn):
        self.title = title
        self.isbn = isbn
        self.is_available = True

class Library:
    def __init__(self, name):
        self.name = name
        self.__books = []      # composition -> Book (owned exclusively)
        self.__members = []    # aggregation -> Member (exists independently)

    def add_book(self, book):
        self.__books.append(book)

    def register_member(self, member):
        self.__members.append(member)

6. Sequence Diagrams

A sequence diagram shows how objects interact over time for one specific scenario/use case — which method is called on which object, and in what order. It's the diagram that helps you verify a class design actually works before you commit to it.

ElementNotation
Actor / ObjectBox at the top of a vertical dashed lifeline
Synchronous callSolid line, filled arrowhead — caller waits for the response
Return messageDashed line, open arrowhead — sent back to the caller
Activation barThin rectangle on a lifeline showing when that object is actively processing
Self-messageArrow that loops back to the same lifeline — an object calling its own method

Worked example: ATM Cash Withdrawal

Solid arrows = synchronous calls · dashed arrows = return values

🎤 When to reach for a sequence diagram in an interview

After you've sketched your classes, walk through the primary use case (e.g. "book a seat", "withdraw cash") as a sequence of calls out loud or on the whiteboard. This is exactly how interviewers verify your class design actually supports the required behavior — and it often reveals a missing method or a misplaced responsibility before you write any code.

📌 Quick Revision — Cheat Sheet

  • Class Diagram = structure (classes + relationships). Sequence Diagram = behavior (call order for one use case). These two cover ~95% of interview usage.
  • Association: plain "uses-a" line. Dependency: same but weaker/temporary, dashed.
  • Aggregation (◇): has-a, part survives without whole. Composition (♦): has-a, part dies with whole.
  • Inheritance (▷): is-a, solid line + hollow triangle at parent. Realization: same triangle but dashed line, used for interface/ABC implementation.
  • Multiplicity: 1, 0..1, 0..*, 1..* written near each end of a relationship.
  • Visibility symbols: + public, - private, # protected, ~ package.
  • Sequence diagrams: solid + filled arrow = sync call; dashed + open arrow = return value; vertical dashed line = lifeline.

7. Common Interview Questions

🎤 Q: Difference between aggregation and composition?

Both represent "has-a" relationships, but composition implies the contained object's lifecycle is fully owned by the container (destroy the container, the part goes with it), while aggregation implies the contained object can exist independently. Classic example: a Car is composed of an Engine (can't exist meaningfully without the car), but a Library only aggregates Members (people exist regardless of library membership).

🎤 Q: Association vs Dependency?

Association is a structural, usually long-lived relationship (often stored as a field, e.g. self.engine). Dependency is a weaker, transient relationship — one class merely uses another briefly, e.g. as a method parameter or local variable, without holding a reference to it long-term.

🎤 Q: How do you show that a class implements an interface?

With a realization relationship: a dashed line with a hollow triangle pointing at the interface/abstract class. In Python this maps to a concrete class inheriting from an ABC and implementing all its @abstractmethods.

🎤 Q: Why bother with a sequence diagram if you already have a class diagram?

A class diagram shows what's possible (structure); it doesn't prove the design actually works for a real use case. Walking through a sequence diagram forces you to trace an actual call path end-to-end, which is how you catch a missing method, a wrong direction of dependency, or a class doing too much (an SRP violation) before writing code.
