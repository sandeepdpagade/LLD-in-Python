Behavioral Design Patterns

Patterns that deal with how objects communicate and distribute responsibility — Strategy, Observer, Command, State, Template Method, and Chain of Responsibility.

🔄 Design Patterns ⏱ ~28 min read 🎯 GoF Behavioral family
💡 Why this matters

Structural patterns compose objects; behavioral patterns decide who talks to whom, and when. This is where most classic LLD interview questions actually live — a Vending Machine is a State machine, a Notification system is an Observer, an Undo feature is a Command, and "handle this request through a chain of approvers" is Chain of Responsibility almost word-for-word.

Overview

1Strategy

Intent: Define a family of interchangeable algorithms, encapsulate each one, and let the client pick/swap which one to use at runtime — without the context class knowing the algorithm's details.

Real-world LLD example: A navigation app that computes a route differently depending on the selected travel mode — Driving, Walking, or Biking.

python
from abc import ABC, abstractmethod

class RouteStrategy(ABC):
    @abstractmethod
    def build_route(self, start, end): pass

class DrivingStrategy(RouteStrategy):
    def build_route(self, start, end):
        return f"Driving route from {start} to {end} via highway"

class WalkingStrategy(RouteStrategy):
    def build_route(self, start, end):
        return f"Walking route from {start} to {end} via footpaths"

class BikingStrategy(RouteStrategy):
    def build_route(self, start, end):
        return f"Biking route from {start} to {end} via bike lanes"

class Navigator:
    def __init__(self, strategy: RouteStrategy):
        self.strategy = strategy

    def set_strategy(self, strategy: RouteStrategy):    # swap at runtime
        self.strategy = strategy

    def get_directions(self, start, end):
        return self.strategy.build_route(start, end)

nav = Navigator(DrivingStrategy())
print(nav.get_directions("Home", "Office"))    # Driving route...

nav.set_strategy(WalkingStrategy())
print(nav.get_directions("Home", "Office"))    # Walking route...
🎤 Interview one-liner

You've already seen this pattern — it's exactly what fixed the Open/Closed Principle violation on the SOLID page (the discount calculator's if/elif chain). Strategy is the standard technique for satisfying OCP when behavior varies by type.

2Observer

Intent: Define a one-to-many relationship so that when one object (the subject) changes state, all its registered dependents (observers) are notified automatically.

Real-world LLD example: A YouTube channel notifying all of its subscribers — across different notification channels — whenever it uploads a new video.

python
from abc import ABC, abstractmethod

class Subscriber(ABC):
    @abstractmethod
    def update(self, video_title): pass

class EmailSubscriber(Subscriber):
    def __init__(self, email): self.email = email
    def update(self, video_title):
        print(f"Email to {self.email}: New video - {video_title}")

class AppSubscriber(Subscriber):
    def update(self, video_title):
        print(f"App notification: New video - {video_title}")

class Channel:                                # the "subject"
    def __init__(self, name):
        self.name = name
        self._subscribers = []

    def subscribe(self, sub: Subscriber):
        self._subscribers.append(sub)

    def unsubscribe(self, sub: Subscriber):
        self._subscribers.remove(sub)

    def upload_video(self, title):
        print(f"{self.name} uploaded: {title}")
        for sub in self._subscribers:          # notify everyone automatically
            sub.update(title)

channel = Channel("TechWithSandeep")
channel.subscribe(EmailSubscriber("me@example.com"))
channel.subscribe(AppSubscriber())
channel.upload_video("Observer Pattern Explained")
# Channel has zero knowledge of HOW each subscriber reacts.
🎤 Interview one-liner

Observer is the pattern behind almost every "notify me when X happens" feature: stock price alerts, event listeners in a GUI, model-view updates. The key property is loose coupling — the subject only knows observers implement update(), never their concrete types.

3Command

Intent: Encapsulate a request as a standalone object, so it can be passed around, queued, logged, or undone — decoupling the object that invokes an action from the object that actually performs it.

Real-world LLD example: A universal remote control app where every button press needs to support undo.

python
from abc import ABC, abstractmethod

class Command(ABC):
    @abstractmethod
    def execute(self): pass
    @abstractmethod
    def undo(self): pass

class Light:                                   # the "receiver" — does the real work
    def turn_on(self): print("Light ON")
    def turn_off(self): print("Light OFF")

class LightOnCommand(Command):
    def __init__(self, light: Light):
        self.light = light
    def execute(self):
        self.light.turn_on()
    def undo(self):
        self.light.turn_off()

class RemoteControl:                           # the "invoker" — knows nothing about Light
    def __init__(self):
        self.history = []

    def press(self, command: Command):
        command.execute()
        self.history.append(command)

    def press_undo(self):
        if self.history:
            self.history.pop().undo()

light = Light()
remote = RemoteControl()
remote.press(LightOnCommand(light))    # Light ON
remote.press_undo()                    # Light OFF -> undo works generically for ANY command
🎤 Interview one-liner

RemoteControl never imports or references Light directly — it only knows the Command interface. That decoupling is what lets the same remote drive a Light, a Fan, or a Thermostat without any changes, and is also what makes undo/redo stacks and macro-recording possible.

4State

Intent: Let an object change its behavior when its internal state changes, so it appears to change its class — instead of one giant method full of if/elif checks on a status flag.

Real-world LLD example: A vending machine that behaves completely differently depending on whether a coin has been inserted yet — a classic LLD interview question in its own right.

python
from abc import ABC, abstractmethod

class VendingState(ABC):
    @abstractmethod
    def insert_coin(self, machine): pass
    @abstractmethod
    def dispense(self, machine): pass

class NoCoinState(VendingState):
    def insert_coin(self, machine):
        print("Coin accepted")
        machine.state = machine.has_coin_state     # transition
    def dispense(self, machine):
        print("Insert a coin first!")

class HasCoinState(VendingState):
    def insert_coin(self, machine):
        print("Coin already inserted, one is enough")
    def dispense(self, machine):
        print("Dispensing item...")
        machine.state = machine.no_coin_state       # transition back

class VendingMachine:
    def __init__(self):
        self.no_coin_state = NoCoinState()
        self.has_coin_state = HasCoinState()
        self.state = self.no_coin_state             # start state

    def insert_coin(self): self.state.insert_coin(self)
    def dispense(self): self.state.dispense(self)

machine = VendingMachine()
machine.dispense()        # Insert a coin first!
machine.insert_coin()     # Coin accepted
machine.dispense()        # Dispensing item...
🚨 Strategy vs State — the classic mix-up

Structurally these two patterns look almost identical (a context object holding a swappable object behind a common interface). The difference is who decides to swap it: in Strategy, the client explicitly picks the algorithm from outside (nav.set_strategy(...)). In State, the state objects themselves trigger the transitions internally (machine.state = machine.has_coin_state) — the object's behavior evolves on its own as events happen.

5Template Method

Intent: Define the overall skeleton of an algorithm in a base class method, deferring only specific steps to subclasses — the sequence of steps never changes, only what happens inside a few of them.

Real-world LLD example: Making a hot beverage always follows the same 4 steps, but "brewing" and "condiments" differ between tea and coffee.

python
from abc import ABC, abstractmethod

class CaffeineBeverage(ABC):
    def prepare(self):                # the template method -> fixed skeleton
        self.boil_water()
        self.brew()
        self.pour_in_cup()
        self.add_condiments()

    def boil_water(self):             # shared step -> same for everyone
        print("Boiling water")

    def pour_in_cup(self):            # shared step -> same for everyone
        print("Pouring into cup")

    @abstractmethod
    def brew(self): pass              # varies per subclass

    @abstractmethod
    def add_condiments(self): pass    # varies per subclass

class Tea(CaffeineBeverage):
    def brew(self): print("Steeping the tea")
    def add_condiments(self): print("Adding lemon")

class Coffee(CaffeineBeverage):
    def brew(self): print("Dripping coffee through the filter")
    def add_condiments(self): print("Adding sugar and milk")

Tea().prepare()      # Boiling water / Steeping the tea / Pouring into cup / Adding lemon
Coffee().prepare()   # same skeleton, different brew + condiments steps
🎤 Template Method vs Strategy

Template Method uses inheritance — a subclass overrides specific steps of an algorithm whose overall shape is fixed by the parent. Strategy uses composition — the entire algorithm is swapped out as one interchangeable object, with no shared skeleton at all. Prefer Strategy when you need runtime flexibility; Template Method when the steps are naturally fixed and known at compile time.

6Chain of Responsibility

Intent: Pass a request along a chain of potential handlers until one of them handles it — decoupling the sender of a request from the specific object that ends up processing it.

Real-world LLD example: An expense approval system where a manager can approve small amounts, but larger amounts must escalate up the chain automatically.

python
from abc import ABC, abstractmethod

class Approver(ABC):
    def __init__(self, next_approver=None):
        self.next_approver = next_approver

    @abstractmethod
    def can_approve(self, amount): pass

    def process(self, amount):
        if self.can_approve(amount):
            print(f"{type(self).__name__} approved ${amount}")
        elif self.next_approver:
            self.next_approver.process(amount)      # pass it along the chain
        else:
            print("No one could approve this request")

class Manager(Approver):
    def can_approve(self, amount): return amount <= 1000

class Director(Approver):
    def can_approve(self, amount): return amount <= 10000

class VP(Approver):
    def can_approve(self, amount): return amount <= 100000

chain = Manager(Director(VP()))    # build the chain: Manager -> Director -> VP

chain.process(500)      # Manager approved $500
chain.process(5000)     # Director approved $5000
chain.process(50000)    # VP approved $50000
chain.process(500000)   # No one could approve this request
🎤 Interview one-liner

The caller (chain.process(amount)) never needs to know or check which specific approver will end up handling the request — it just hands it to the front of the chain. This is the same underlying idea as middleware pipelines, event bubbling in the DOM, and support-ticket escalation (L1 → L2 → L3).

📌 Quick Revision — Cheat Sheet

  • Strategy — swap the whole algorithm, client decides. Composition-based.
  • Observer — subject auto-notifies a list of registered observers on change.
  • Command — wrap a request as an object; enables undo, queuing, logging, decoupled invokers.
  • State — behavior changes automatically as the object's internal state transitions.
  • Template Method — fixed algorithm skeleton in the base class; subclasses override specific steps. Inheritance-based.
  • Chain of Responsibility — pass a request along a chain until a handler accepts it.
  • Strategy vs State: who swaps the behavior — the client (Strategy) or the object itself (State)?
  • Template Method vs Strategy: fixed skeleton + inheritance (Template Method) vs fully swappable + composition (Strategy).

Common Interview Questions

🎤 Q: How would you design a Vending Machine? Which pattern fits?

State is the textbook fit — model each machine mode (NoCoin, HasCoin, Dispensing, SoldOut) as its own class implementing a shared interface, and let each state decide both what happens and which state comes next. This avoids one giant method full of nested if checks on a status flag.

🎤 Q: Observer vs a Pub/Sub message broker — same thing?

Conceptually similar (notify interested parties on an event) but different in coupling and scope. Observer is typically in-process and direct — the subject holds direct references to its observers. Pub/Sub adds a broker/message queue between publishers and subscribers, so they don't know about each other at all, and it usually spans multiple processes or services.

🎤 Q: Why not just call the receiver's method directly instead of using Command?

Direct calls work fine until you need one of: queuing/deferring the action, logging what happened, supporting undo/redo, or letting the same invoker (e.g. a generic button/menu item) trigger completely different receivers interchangeably. Command earns its complexity specifically when one of those needs shows up — don't reach for it by default.

🎤 Q: In Chain of Responsibility, what happens if no handler can process the request?

You must explicitly decide: either the last handler has a fallback/default behavior (as in the example, printing a rejection), or the chain throws an exception. Silently dropping the request is a common design bug in real implementations — always design the "nobody handled this" case on purpose.
