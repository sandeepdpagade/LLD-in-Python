Structural Design Patterns

Patterns that deal with how classes and objects are composed together — Adapter, Decorator, Facade, Composite, and Proxy.

🧩 Design Patterns ⏱ ~25 min read 🎯 GoF Structural family
💡 Why this matters

Structural patterns are all about composing existing classes into larger structures without touching their source code. All five patterns on this page achieve this by wrapping one object inside another — the differences between them are almost entirely about intent, which makes them easy to confuse. Pay close attention to the comparison table near the bottom.

Overview

PatternSolvesOne-line rule
AdapterTwo incompatible interfaces need to work togetherWrap one interface to look like another
DecoratorNeed to add behavior without subclass explosionWrap an object to add responsibilities, same interface
FacadeA subsystem has too many moving parts to use directlyWrap many classes behind one simple interface
CompositeNeed to treat single objects and groups identicallyTree structure where nodes and leaves share an interface
ProxyNeed to control/delay/guard access to an objectWrap an object with the same interface to intercept access

1Adapter

Intent: Convert the interface of one class into another interface the client expects, so two otherwise-incompatible pieces of code can work together — without modifying either one.

Real-world LLD example: You integrate a third-party payment SDK whose method is make_payment(amount_in_cents), but your app's checkout code is built around a PaymentProcessor.pay(amount_in_dollars) interface.

python
from abc import ABC, abstractmethod

# Your app's expected interface
class PaymentProcessor(ABC):
    @abstractmethod
    def pay(self, amount_dollars: float): pass

# A third-party SDK you can't modify — incompatible interface
class StripeSDK:
    def make_payment(self, amount_cents: int):
        print(f"Charged {amount_cents} cents via Stripe")

# Adapter bridges the gap
class StripeAdapter(PaymentProcessor):
    def __init__(self, stripe_sdk: StripeSDK):
        self.stripe_sdk = stripe_sdk

    def pay(self, amount_dollars: float):
        cents = int(amount_dollars * 100)
        self.stripe_sdk.make_payment(cents)     # translates the call

def checkout(processor: PaymentProcessor, amount: float):
    processor.pay(amount)

checkout(StripeAdapter(StripeSDK()), 19.99)   # Charged 1999 cents via Stripe
# checkout() only ever talks to PaymentProcessor -> never needs to know Stripe exists
🎤 Interview one-liner

Adapter is what you reach for whenever you say "I need to plug in a third-party library / legacy class that doesn't match my interface." It changes the interface — the behavior underneath stays exactly the same.

2Decorator

Intent: Attach new behavior to an object dynamically by wrapping it, as a flexible alternative to subclassing every possible combination of features.

Real-world LLD example: A coffee shop ordering system where a base Coffee can have any combination of Milk, Sugar, Whip — creating a subclass for every combination (MilkSugarCoffee, MilkWhipCoffee...) would explode combinatorially.

python
from abc import ABC, abstractmethod

class Coffee(ABC):
    @abstractmethod
    def cost(self) -> float: pass
    @abstractmethod
    def description(self) -> str: pass

class SimpleCoffee(Coffee):
    def cost(self): return 2.0
    def description(self): return "Coffee"

class CoffeeDecorator(Coffee):              # wraps a Coffee, matches Coffee's interface
    def __init__(self, coffee: Coffee):
        self._coffee = coffee
    def cost(self): return self._coffee.cost()
    def description(self): return self._coffee.description()

class MilkDecorator(CoffeeDecorator):
    def cost(self): return self._coffee.cost() + 0.5
    def description(self): return self._coffee.description() + " + Milk"

class SugarDecorator(CoffeeDecorator):
    def cost(self): return self._coffee.cost() + 0.2
    def description(self): return self._coffee.description() + " + Sugar"

order = SugarDecorator(MilkDecorator(SimpleCoffee()))
print(order.description(), "->", f"${order.cost()}")
# Coffee + Milk + Sugar -> $2.7
# Any combination, in any order, with zero new subclasses.
⚠️ Don't confuse this with Python's @decorator syntax

Python's @my_decorator function syntax is a language feature for wrapping functions (e.g. @staticmethod, @property, @app.route). The Decorator design pattern above is a separate, broader OOP concept about wrapping objects to add behavior — they share a name and a similar idea ("wrap to extend"), but are not the same thing. Interviewers sometimes ask you to point out this distinction explicitly.

3Facade

Intent: Provide a single, simplified interface to a complex subsystem made up of many interacting classes, hiding that complexity from the client.

Real-world LLD example: Placing an order touches inventory, payment, and shipping subsystems — the client shouldn't need to know or coordinate all three.

python
class InventoryService:
    def check_stock(self, item):
        print(f"Checking stock for {item}...")
        return True

class PaymentService:
    def charge(self, amount):
        print(f"Charging ${amount}...")

class ShippingService:
    def ship(self, item):
        print(f"Shipping {item}...")

class OrderFacade:                          # one simple entry point
    def __init__(self):
        self.inventory = InventoryService()
        self.payment = PaymentService()
        self.shipping = ShippingService()

    def place_order(self, item, amount):
        if self.inventory.check_stock(item):
            self.payment.charge(amount)
            self.shipping.ship(item)
            print("Order placed!")

OrderFacade().place_order("Laptop", 999)
# Client calls ONE method; never touches Inventory/Payment/Shipping directly.
🎤 Interview one-liner

Facade doesn't add new behavior or change any interface — it just hides orchestration complexity. The subsystem classes still exist and can still be used directly by code that needs finer control; the Facade is a convenience layer, not a replacement.

4Composite

Intent: Compose objects into tree structures representing part-whole hierarchies, so client code can treat an individual object and a group of objects uniformly, through the same interface.

Real-world LLD example: A file system, where a Folder can contain both Files and other Folders, and you want get_size() to work identically on either.

python
from abc import ABC, abstractmethod

class FileSystemItem(ABC):
    @abstractmethod
    def get_size(self) -> int: pass

class File(FileSystemItem):                 # leaf
    def __init__(self, name, size):
        self.name = name
        self.size = size
    def get_size(self):
        return self.size

class Folder(FileSystemItem):               # composite -> holds other FileSystemItems
    def __init__(self, name):
        self.name = name
        self.children = []
    def add(self, item: FileSystemItem):
        self.children.append(item)
    def get_size(self):
        return sum(child.get_size() for child in self.children)

root = Folder("root")
root.add(File("resume.pdf", 200))
docs = Folder("docs")
docs.add(File("notes.txt", 50))
docs.add(File("photo.png", 500))
root.add(docs)

print(root.get_size())    # 750 -> works whether children are Files or nested Folders
🎤 Interview one-liner

Composite is the pattern behind any recursive "tree" structure: file systems, UI component hierarchies (a Panel containing Buttons and other Panels), org charts (an Employee that may or may not manage other Employees). The tell is when client code says "I don't care if this is one item or a group of items."

5Proxy

Intent: Provide a stand-in object with the same interface as a real object, to control access to it — for lazy loading, access control, caching, or logging, without the client knowing the difference.

Real-world LLD example: A large image that shouldn't be loaded from disk until it's actually displayed (lazy loading).

python
from abc import ABC, abstractmethod

class Image(ABC):
    @abstractmethod
    def display(self): pass

class RealImage(Image):
    def __init__(self, filename):
        self.filename = filename
        self._load_from_disk()              # expensive!
    def _load_from_disk(self):
        print(f"Loading {self.filename} from disk...")
    def display(self):
        print(f"Displaying {self.filename}")

class ProxyImage(Image):                     # same interface as RealImage
    def __init__(self, filename):
        self.filename = filename
        self._real_image = None              # not loaded yet

    def display(self):
        if self._real_image is None:         # lazy initialization
            self._real_image = RealImage(self.filename)
        self._real_image.display()

image = ProxyImage("vacation.jpg")           # nothing loaded yet
image.display()   # Loading vacation.jpg from disk... / Displaying vacation.jpg
image.display()   # Displaying vacation.jpg  -> already loaded, no repeat disk hit

The "Wrapper Pattern" Comparison

Adapter, Decorator, Facade, and Proxy all wrap another object — this table is the fastest way to keep them straight in an interview:

PatternChanges the interface?Changes/adds behavior?Number of objects wrapped
AdapterYes — translates to a different interfaceNo — same behavior, different shapeOne
DecoratorNo — same interfaceYes — adds new behavior/responsibilityOne (nestable)
FacadeYes — offers a new, simpler interfaceNo — just orchestrates existing behaviorMany (a whole subsystem)
ProxyNo — identical interfaceNo new behavior — controls access (lazy load, auth, cache)One

📌 Quick Revision — Cheat Sheet

  • Adapter — makes two incompatible interfaces work together. "Translator."
  • Decorator — adds behavior dynamically, same interface, stackable. "Add-ons."
  • Facade — one simple interface hiding a complex subsystem. "Front desk."
  • Composite — tree of objects, leaf and group share one interface. "Uniform recursion."
  • Proxy — same interface, controls access (lazy-load/cache/auth/log). "Gatekeeper."
  • Adapter/Decorator/Proxy all wrap one object; Facade wraps many; Composite wraps a whole tree of them.

Common Interview Questions

🎤 Q: Adapter vs Facade — both simplify usage of another class, what's the difference?

Adapter wraps one incompatible object to make it match an interface the client already expects — it's about interface translation. Facade wraps many classes in a subsystem to expose one simplified interface for convenience — it's about hiding orchestration complexity, not translating a mismatched interface.

🎤 Q: Decorator vs Proxy — both wrap one object with the same interface, what's different?

Decorator's whole purpose is to add new behavior/responsibility to the wrapped object (e.g. adding milk to coffee). Proxy's purpose is to control access to the wrapped object without changing what it fundamentally does (lazy-loading, permission checks, caching) — the underlying operation's result is the same, just gated or optimized.

🎤 Q: How is Composite different from a plain list of objects?

A plain list just stores items — calling code still has to know how to handle a nested list vs a single item. Composite makes the container (Folder) implement the same interface as the individual item (File), so client code can call get_size() on either without ever checking "is this a leaf or a group?"

🎤 Q: Give an example where you'd chain multiple Decorators together.

Web middleware/logging pipelines: wrapping a request handler with a LoggingDecorator, then an AuthDecorator, then a RateLimitDecorator — each adds one responsibility while preserving the same "handle request" interface, and they can be composed in any order.
