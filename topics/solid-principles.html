SOLID Principles

The five design principles interviewers use to judge whether your LLD is actually good — each with a violation and a fix.

🏛 Fundamentals ⏱ ~25 min read 🎯 The #1 evaluation rubric in LLD rounds
💡 Why this matters

SOLID isn't a topic you get asked to "define" — it's the lens interviewers use to critique everything you design. When they ask "what happens if we add a new payment type?" or "what if two classes need slightly different behavior?", they're really asking "did you follow OCP / LSP here?" Knowing the fix cold, not just the name, is what separates a pass from a borderline reject.

SSingle Responsibility Principle (SRP)

"A class should have only one reason to change." Each class should own exactly one piece of responsibility/business logic. If you find yourself describing a class with "and" ("this class calculates the invoice and saves it and prints it"), it's doing too much.

❌ Violation
python
class Invoice:
    def __init__(self, items):
        self.items = items

    def calculate_total(self):
        return sum(item["price"] for item in self.items)

    def save_to_database(self):           # persistence logic
        print("Saving invoice to database...")

    def print_invoice(self):              # presentation logic
        total = self.calculate_total()
        print(f"Invoice total: ${total}")

# Invoice now has 3 reasons to change: a pricing rule changes,
# the database changes, OR the print format changes.
✅ Fix
python
class Invoice:                            # only owns invoice data + pricing
    def __init__(self, items):
        self.items = items

    def calculate_total(self):
        return sum(item["price"] for item in self.items)

class InvoiceRepository:                  # only owns persistence
    def save(self, invoice: Invoice):
        print("Saving invoice to database...")

class InvoicePrinter:                     # only owns presentation
    def print(self, invoice: Invoice):
        print(f"Invoice total: ${invoice.calculate_total()}")

invoice = Invoice(items=[{"price": 100}, {"price": 250}])
InvoiceRepository().save(invoice)
InvoicePrinter().print(invoice)
🎤 How to spot SRP violations in an interview

Ask yourself: "who are the different actors/stakeholders that could request a change to this class?" If the DBA wants to change how data is stored, the finance team wants to change how totals are calculated, and the design team wants to change print formatting — that's 3 actors, 3 responsibilities, 3 classes.

OOpen/Closed Principle (OCP)

"Software entities should be open for extension, but closed for modification." You should be able to add new behavior without editing existing, already-tested code — typically achieved via abstraction + polymorphism instead of conditional branching.

❌ Violation
python
class DiscountCalculator:
    def calculate(self, customer_type, amount):
        if customer_type == "regular":
            return amount
        elif customer_type == "premium":
            return amount * 0.9
        elif customer_type == "vip":
            return amount * 0.8
        # Adding a new customer type means editing this method again
        # and risking breaking the existing, already-tested branches.
✅ Fix
python
from abc import ABC, abstractmethod

class DiscountStrategy(ABC):
    @abstractmethod
    def apply(self, amount: float) -> float:
        pass

class RegularDiscount(DiscountStrategy):
    def apply(self, amount): return amount

class PremiumDiscount(DiscountStrategy):
    def apply(self, amount): return amount * 0.9

class VipDiscount(DiscountStrategy):
    def apply(self, amount): return amount * 0.8

# New requirement -> add a NEW class, touch NOTHING else:
class StudentDiscount(DiscountStrategy):
    def apply(self, amount): return amount * 0.85

def checkout(amount: float, strategy: DiscountStrategy):
    return strategy.apply(amount)

print(checkout(1000, VipDiscount()))       # 800.0
print(checkout(1000, StudentDiscount()))   # 850.0 -> zero changes to checkout()
🎤 Interview one-liner

OCP is basically "replace if/elif chains on a type with polymorphism." This is the exact mechanism behind the Strategy and Factory design patterns — expect to apply it whenever an interviewer says "how would this handle a new type of X in the future?"

LLiskov Substitution Principle (LSP)

"Objects of a superclass should be replaceable with objects of a subclass without breaking the program." If code works correctly with a base class, it must keep working correctly when any subclass is swapped in — a subclass shouldn't weaken guarantees or produce surprising behavior.

❌ Violation — the classic Rectangle/Square trap
python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def set_width(self, w): self.width = w
    def set_height(self, h): self.height = h
    def area(self): return self.width * self.height

class Square(Rectangle):                 # "a square IS-A rectangle", right?
    def set_width(self, w):
        self.width = w
        self.height = w                  # forced to keep both sides equal
    def set_height(self, h):
        self.width = h
        self.height = h

def resize_and_check(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(4)
    assert rect.area() == 20, "Broken!"  # true for Rectangle, but...

resize_and_check(Rectangle(2, 3))   # OK, area = 20
resize_and_check(Square(2, 2))      # AssertionError! area = 16
# Square silently changed set_height's contract -> substitution breaks the caller.
✅ Fix — don't force an is-a where behavior actually differs
python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float:
        pass

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height
    def area(self):
        return self.width * self.height

class Square(Shape):                      # sibling, NOT a subclass of Rectangle
    def __init__(self, side):
        self.side = side
    def area(self):
        return self.side ** 2

def print_area(shape: Shape):
    print(shape.area())

print_area(Rectangle(5, 4))   # 20 -> any Shape works safely, no surprises
print_area(Square(4))         # 16
❌ Another classic violation — the flightless bird trap
python
class Bird:
    def fly(self):
        return "Flying high!"

class Ostrich(Bird):              # an ostrich IS-A bird, but...
    def fly(self):
        raise Exception("Ostriches can't fly!")   # breaks the parent's contract

def make_it_fly(bird: Bird):
    print(bird.fly())

for b in [Bird(), Ostrich()]:
    make_it_fly(b)                # crashes on Ostrich -> not substitutable
✅ Fix — separate "can fly" from "is a bird"
python
from abc import ABC, abstractmethod

class Bird(ABC):
    @abstractmethod
    def move(self): pass

class FlyingBird(Bird):
    def move(self): return "Flying high!"

class Ostrich(Bird):              # no longer promises to fly
    def move(self): return "Running fast!"

def make_it_move(bird: Bird):
    print(bird.move())            # every Bird can be substituted safely

for b in [FlyingBird(), Ostrich()]:
    make_it_move(b)
🚨 The takeaway, generalized

LSP violations usually hide behind an innocent-sounding "is-a": a Square mathematically is a rectangle, and an Ostrich biologically is a bird — but neither behaves like the base type once you add a method (set_width, fly) that not every subtype can honor. Whenever a subclass overrides a method to narrow preconditions, weaken postconditions, or throw on inputs the parent accepted, that's an LSP smell. Prefer modeling shared behavior via a common interface instead of forcing inheritance.

IInterface Segregation Principle (ISP)

"Clients should not be forced to depend on methods they do not use." Prefer several small, focused interfaces over one large, general-purpose one.

❌ Violation
python
from abc import ABC, abstractmethod

class Worker(ABC):
    @abstractmethod
    def work(self): pass

    @abstractmethod
    def eat(self): pass

class HumanWorker(Worker):
    def work(self): print("Coding...")
    def eat(self): print("Eating lunch...")

class RobotWorker(Worker):
    def work(self): print("Welding...")
    def eat(self):
        raise NotImplementedError("Robots don't eat!")
        # Forced to implement a method that makes no sense for this class.
✅ Fix
python
from abc import ABC, abstractmethod

class Workable(ABC):
    @abstractmethod
    def work(self): pass

class Eatable(ABC):
    @abstractmethod
    def eat(self): pass

class HumanWorker(Workable, Eatable):     # needs both -> implements both
    def work(self): print("Coding...")
    def eat(self): print("Eating lunch...")

class RobotWorker(Workable):              # only needs Workable -> only implements that
    def work(self): print("Welding...")

def start_shift(worker: Workable):
    worker.work()

start_shift(HumanWorker())
start_shift(RobotWorker())    # no forced, meaningless eat() method anywhere
🎤 Interview one-liner

ISP is SRP applied to interfaces/abstract classes instead of concrete classes. If an ABC has methods that only some subclasses can meaningfully implement, split it — a "fat interface" forces classes to implement (or stub out / raise on) methods irrelevant to them.

DDependency Inversion Principle (DIP)

"High-level modules should not depend on low-level modules — both should depend on abstractions." Business logic shouldn't be wired directly to a concrete implementation detail (a specific database, email provider, payment gateway); it should depend on an interface, with the concrete class "injected" from outside.

❌ Violation
python
class EmailSender:
    def send(self, message):
        print(f"Emailing: {message}")

class NotificationService:                # high-level module
    def __init__(self):
        self.sender = EmailSender()       # hard-wired to ONE concrete class
        # low-level module (EmailSender) directly created inside high-level module

    def notify(self, message):
        self.sender.send(message)

# Switching to SMS later means editing NotificationService's source code.
✅ Fix
python
from abc import ABC, abstractmethod

class MessageSender(ABC):                 # the abstraction both sides depend on
    @abstractmethod
    def send(self, message): pass

class EmailSender(MessageSender):
    def send(self, message):
        print(f"Emailing: {message}")

class SMSSender(MessageSender):
    def send(self, message):
        print(f"Texting: {message}")

class NotificationService:                # high-level module
    def __init__(self, sender: MessageSender):   # depends on the abstraction
        self.sender = sender              # injected from outside ("dependency injection")

    def notify(self, message):
        self.sender.send(message)

NotificationService(EmailSender()).notify("Order shipped!")
NotificationService(SMSSender()).notify("Order shipped!")   # swap freely, zero edits above
💡 DIP vs Dependency Injection — not the same thing

DIP is the design principle ("depend on abstractions"). Dependency Injection (DI) is one common technique for achieving it (passing the concrete implementation in via constructor/parameter, as above). You can follow DIP without a DI framework — plain constructor injection, like this example, is enough for almost every LLD interview.

📌 Quick Revision — Cheat Sheet

  • S — One class, one reason to change. Split by actor/stakeholder, not by convenience.
  • O — Add new behavior via a new class, not by editing existing if/elif chains. Powers Strategy/Factory patterns.
  • L — A subclass must honor the base class's contract fully. If overriding narrows/breaks behavior (Rectangle/Square), don't force inheritance.
  • I — Many small, focused interfaces > one fat interface. Don't make a class implement methods it can't honestly support.
  • D — High-level business logic depends on an abstraction (ABC), not a concrete class. Inject the concrete implementation from outside.

Common Interview Questions

🎤 Q: Which SOLID principle is violated most often in real code?

SRP, by far — classes that quietly accumulate persistence, validation, and formatting logic alongside their core responsibility ("God classes"). It's also the easiest one to fix incrementally, which is why interviewers probe it first.

🎤 Q: How are OCP and the Strategy pattern related?

Strategy is a direct implementation technique for OCP: instead of branching on type inside one method, you extract each behavior into its own class behind a common interface, and the context class picks which one to use at runtime — extending behavior without modifying existing code.

🎤 Q: Give a real example of an LSP violation you'd catch in review.

A subclass that overrides a method to throw an exception for cases the parent handled fine (like RobotWorker.eat() raising in the ISP example, if it had been forced to inherit `eat()`), or one that returns a different/narrower type than callers expect. Any time substituting the subclass in existing code could break it, that's LSP.

🎤 Q: Does following DIP mean you always need a dependency injection framework?

No — in Python, plain constructor injection (passing the dependency as a parameter, as shown above) is enough for almost all LLD problems. Frameworks like dependency-injector just automate wiring for large real-world apps; interviewers care about the principle, not the tooling.
