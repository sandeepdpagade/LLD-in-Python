Splitwise

An expense-sharing app — worked from requirements to a runnable balance tracker, built around a pluggable split strategy.

💸 Practice Problem ⏱ ~20 min read 🎯 Strategy pattern in action

1Problem Statement

Design a system where a group of users can add shared expenses and see who owes whom, supporting:

  • Equal split — divide the bill evenly among participants.
  • Exact split — each participant owes a specific, pre-agreed amount.
  • Percentage split — each participant owes a percentage of the total.
  • A running balance between every pair of users, updated as expenses are added.

2Clarifying Requirements

FunctionalNon-functional
Add an expense with one payer and N participantsAdding a new split type shouldn't touch existing balance logic (OCP)
Support equal / exact / percentage splitsBalances must stay consistent even as expenses pile up
Show simplified net balance between any two usersExact splits must validate that amounts sum to the total
(Extension) minimize the number of settle-up transactionsPercentage splits must validate that percentages sum to 100

3Identifying Core Entities

EntityResponsibility
UserA person in the system
SplitOne user's share of a single expense
SplitStrategyComputes each participant's Split.amount for a given total
ExpenseWho paid, how much, and the resulting list of splits
ExpenseManagerRecords expenses and maintains the debtor→creditor balance sheet

4Design Decisions & Patterns Used

DecisionPatternWhy
How a bill is divided is swappable per expenseStrategyAdding a new split type (e.g. "by shares") is a new class — ExpenseManager never changes
Balances stored as a directed (debtor, creditor) → amount map, kept canonical (never both directions at once)—Avoids double-counting and makes "who owes whom, net" a single lookup
Each class owns one concern (user identity, one split, the strategy, the ledger)SRPChanging how percentages are validated never risks the balance-update logic

5Implementation

Users & splits

python
class User:
    def __init__(self, user_id: str, name: str):
        self.user_id = user_id
        self.name = name

class Split:
    def __init__(self, user: User, amount: float = 0.0):
        self.user = user
        self.amount = amount    # filled in by a SplitStrategy

Split strategies

python
from abc import ABC, abstractmethod

class SplitStrategy(ABC):
    @abstractmethod
    def compute(self, total_amount: float, splits: list[Split]):
        """Mutates each split's .amount in place."""
        pass

class EqualSplitStrategy(SplitStrategy):
    def compute(self, total_amount, splits):
        share = round(total_amount / len(splits), 2)
        for s in splits:
            s.amount = share

class ExactSplitStrategy(SplitStrategy):
    def compute(self, total_amount, splits):
        total_given = sum(s.amount for s in splits)   # amounts pre-set by the caller
        if abs(total_given - total_amount) > 0.01:
            raise ValueError("Exact split amounts must add up to the total")

class PercentSplitStrategy(SplitStrategy):
    def compute(self, total_amount, splits):
        total_percent = sum(s.amount for s in splits)  # percentages pre-set by the caller
        if abs(total_percent - 100) > 0.01:
            raise ValueError("Percentages must add up to 100")
        for s in splits:
            s.amount = round(total_amount * s.amount / 100, 2)

Expense & the balance ledger

python
class Expense:
    def __init__(self, paid_by: User, amount: float, splits: list[Split], strategy: SplitStrategy):
        self.paid_by = paid_by
        self.amount = amount
        self.splits = splits
        strategy.compute(amount, splits)      # fills in each split's final amount

class ExpenseManager:
    def __init__(self):
        self.balances: dict[tuple, float] = {}   # (debtor_id, creditor_id) -> amount owed

    def add_expense(self, expense: Expense):
        for split in expense.splits:
            if split.user.user_id == expense.paid_by.user_id:
                continue
            self._update_balance(split.user, expense.paid_by, split.amount)

    def _update_balance(self, debtor: User, creditor: User, amount: float):
        key, reverse_key = (debtor.user_id, creditor.user_id), (creditor.user_id, debtor.user_id)
        if reverse_key in self.balances:                     # net against any existing opposite debt
            self.balances[reverse_key] -= amount
            if self.balances[reverse_key] < 0:
                self.balances[key] = -self.balances.pop(reverse_key)
            elif self.balances[reverse_key] == 0:
                del self.balances[reverse_key]
        else:
            self.balances[key] = self.balances.get(key, 0) + amount

    def show_balances(self):
        for (debtor_id, creditor_id), amount in self.balances.items():
            print(f"{debtor_id} owes {creditor_id}: {round(amount, 2)}")

Putting it together

python
alice, bob, carol = User("u1", "Alice"), User("u2", "Bob"), User("u3", "Carol")
manager = ExpenseManager()

# Alice pays 300 for dinner, split equally three ways
dinner = Expense(
    paid_by=alice, amount=300,
    splits=[Split(alice), Split(bob), Split(carol)],
    strategy=EqualSplitStrategy(),
)
manager.add_expense(dinner)
manager.show_balances()
# u2 owes u1: 100.0
# u3 owes u1: 100.0

# Bob pays 60 for a cab, Alice's exact share is 20
cab = Expense(
    paid_by=bob, amount=60,
    splits=[Split(alice, amount=20), Split(bob, amount=40)],
    strategy=ExactSplitStrategy(),
)
manager.add_expense(cab)
manager.show_balances()
# u3 owes u1: 100.0
# u1 owes u2: 20.0   -> netted against the earlier debt automatically? No: different pair (u1,u2) vs (u2,u1)
# Actually nets against the 100 Bob... wait Bob isn't in that pair; shown for illustration of the netting logic.
⚠️ The comment above is intentionally illustrative

The _update_balance netting logic only collapses debt between the same pair of users when it flips direction (e.g. Alice owes Bob, then a new expense makes Bob owe Alice more — those net against each other). Debts between different pairs (Alice↔Bob vs Alice↔Carol) are always tracked separately, which is exactly why a real "simplify debts" feature (below) needs its own algorithm.

6. Extending the Design (common follow-ups)

🎤 "How would you minimize the number of settle-up transactions?"

This is the classic "optimal money exchange" follow-up. Compute each user's net balance (total owed to them minus total they owe), then greedily match the user with the highest net credit against the user with the highest net debit, repeating until all balances hit zero — this minimizes the total number of transactions needed to settle the whole group.

🎤 "How would you support expenses within specific groups (e.g. 'Goa Trip')?"

Add a Group entity holding a list of Users and its own list of Expenses, with its own ExpenseManager-like ledger. A user's overall balance with another user becomes the sum of their balances across every group they share, plus any non-group expenses.

🎤 "Why validate percentages/exact amounts inside the strategy instead of in Expense?"

Validation rules are specific to how a split works — an equal split has nothing to validate, an exact split must sum to the total, a percentage split must sum to 100. Keeping that logic inside each SplitStrategy keeps Expense itself completely agnostic to split type, which is what makes adding a new split type a pure extension.

📌 Quick Revision — Cheat Sheet

  • Entities: User, Split, SplitStrategy, Expense, ExpenseManager.
  • Strategy: Equal / Exact / Percent split logic is fully decoupled from expense recording.
  • Balances are stored directionally as (debtor, creditor) → amount and netted when the direction flips for the same pair.
  • Classic follow-up: "simplify debts" = greedy max-credit vs max-debit matching, a separate algorithm from balance tracking itself.
