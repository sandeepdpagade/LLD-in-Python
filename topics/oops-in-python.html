OOP in Python

Everything you need to confidently answer OOP questions in an LLD interview — with runnable examples.

🧱 Fundamentals ⏱ ~25 min read 🎯 High interview frequency
💡 Why this matters

Every LLD interview (Parking Lot, Elevator System, BookMyShow, Splitwise...) is graded on how well you model the real world using classes. If your OOP fundamentals are shaky, the whole design falls apart — so this is the highest-leverage topic to master first.

1. What is OOP?

Object-Oriented Programming is a paradigm that organizes code around objects — bundles of data (attributes) and behavior (methods) — instead of just functions acting on raw data. Python is a fully object-oriented language: even integers and functions are objects.

OOP is built on 4 pillars, which is almost always the first thing interviewers ask you to name:

PillarOne-line definition
EncapsulationBundling data + methods together, and restricting direct access to internal state
AbstractionHiding implementation details, exposing only what's necessary
InheritanceAcquiring properties/behavior of a parent class in a child class
PolymorphismSame interface, different underlying implementation/behavior

All 4 in one glance, using a Vault class you'll recognize the shape of throughout this page:

python
from abc import ABC, abstractmethod

class Storage(ABC):                    # Abstraction: a contract, no implementation
    @abstractmethod
    def unlock(self, code): pass

class Vault(Storage):                  # Inheritance: Vault IS-A Storage
    def __init__(self, pin):
        self.__pin = pin                # Encapsulation: pin is hidden (name-mangled)

    def unlock(self, code):             # Polymorphism: overrides Storage's contract
        return "Unlocked!" if code == self.__pin else "Wrong code"

print(Vault(1234).unlock(1234))         # Unlocked!

2. Classes and Objects

A class is a blueprint. An object (a.k.a. instance) is a concrete thing built from that blueprint, with its own copy of the data.

python
class Car:
    pass

# Objects / instances
car1 = Car()
car2 = Car()

print(type(car1))          # <class '__main__.Car'>
print(car1 is car2)        # False -> different objects in memory

3. __init__ and self

__init__ is the constructor — it runs automatically right after an object is created, and is used to initialize instance attributes. self is a reference to the current instance; it must be the first parameter of every instance method (Python passes it automatically, you never pass it manually).

python
class Car:
    def __init__(self, brand, model):
        self.brand = brand      # instance attribute
        self.model = model

    def describe(self):
        return f"{self.brand} {self.model}"

car1 = Car("Toyota", "Corolla")
car2 = Car("Honda", "Civic")

print(car1.describe())   # Toyota Corolla
print(car2.describe())   # Honda Civic
⚠️ Common gotcha

__init__ is not a constructor in the strict sense — __new__ actually creates the object; __init__ only initializes it. This distinction occasionally comes up when discussing singletons or immutable types.

4. Instance Variables vs Class Variables

  • Instance variables: defined inside methods using self.x. Unique to each object.
  • Class variables: defined directly inside the class body. Shared across all instances.
python
class Car:
    wheels = 4  # class variable — shared by every Car

    def __init__(self, brand):
        self.brand = brand  # instance variable — unique per object

car1 = Car("Toyota")
car2 = Car("Honda")

print(car1.wheels, car2.wheels)  # 4 4

Car.wheels = 6          # change on the class
print(car1.wheels)      # 6 -> reflected everywhere

car1.wheels = 3         # this creates a NEW instance attribute on car1 only!
print(car1.wheels, car2.wheels)   # 3 6
🚨 Classic pitfall — mutable class variables

Never use a mutable default (list/dict) as a class variable if you expect per-instance data — all instances will share and mutate the same object.

python
class Bad:
    items = []  # shared across ALL instances!
    def add(self, x):
        self.items.append(x)

a, b = Bad(), Bad()
a.add(1)
print(b.items)   # [1]  <- leaked into b! Almost never what you want.

# Fix: initialize per-instance in __init__
class Good:
    def __init__(self):
        self.items = []

5. Instance Methods vs Class Methods vs Static Methods

TypeDecoratorFirst argUse case
Instance methodnoneselfOperates on/reads instance state
Class method@classmethodclsOperates on class state; alternate constructors
Static method@staticmethodnoneUtility function logically grouped with the class
python
class Employee:
    company = "Acme Corp"

    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def give_raise(self, amount):          # instance method
        self.salary += amount

    @classmethod
    def from_string(cls, data_str):        # alternate constructor
        name, salary = data_str.split("-")
        return cls(name, int(salary))

    @classmethod
    def change_company(cls, new_name):     # modifies class-level state
        cls.company = new_name

    @staticmethod
    def is_valid_salary(salary):           # pure utility, no self/cls needed
        return salary > 0

e1 = Employee.from_string("Alice-50000")
print(e1.name, e1.salary)                  # Alice 50000
print(Employee.is_valid_salary(-100))      # False
🎤 Interview one-liner

"Use @classmethod when the logic needs the class itself (e.g. factory methods like from_json), and @staticmethod when the logic is related to the class conceptually but needs neither self nor cls."

6. Encapsulation

Encapsulation means restricting direct access to an object's internals and exposing controlled access through methods/properties. Python doesn't have true "private" members (no strict access modifiers) — it relies on naming conventions.

ConventionMeaningEnforced?
public_varPublic — accessible anywhere—
_protected_varConvention: internal use / subclasses onlyNo, just a hint
__private_varName-mangled to _ClassName__private_varMostly — discourages accidental access
python
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance   # name-mangled -> _BankAccount__balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.__balance += amount

    def get_balance(self):
        return self.__balance

acc = BankAccount(1000)
acc.deposit(500)
print(acc.get_balance())     # 1500
print(acc._BankAccount__balance)  # 1500 -> still technically accessible!

The Pythonic way: @property

Instead of writing Java-style get_x()/set_x(), Python uses the @property decorator to expose controlled access while keeping the clean attribute syntax (obj.x instead of obj.get_x()).

python
class Temperature:
    def __init__(self, celsius):
        self._celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("Below absolute zero!")
        self._celsius = value

    @property
    def fahrenheit(self):              # read-only computed property
        return self._celsius * 9 / 5 + 32

t = Temperature(25)
print(t.celsius)        # 25          (looks like an attribute)
print(t.fahrenheit)     # 77.0        (computed on the fly)
t.celsius = 30          # goes through the setter's validation
t.celsius = -300        # raises ValueError

7. Inheritance

Inheritance lets a class (child/subclass) reuse and extend the attributes/methods of another class (parent/superclass) — an "is-a" relationship (a Dog is an Animal).

python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return "..."

class Dog(Animal):
    def speak(self):               # method overriding
        return f"{self.name} says Woof!"

class Puppy(Dog):
    def speak(self):
        parent_sound = super().speak()   # call parent's implementation
        return f"{parent_sound} (but tiny)"

p = Puppy("Rex")
print(p.speak())   # Rex says Woof! (but tiny)
print(isinstance(p, Animal))   # True -> Puppy IS-A Animal too

Types of inheritance

TypeDescription
Singleclass B(A) — one parent, one child
Multilevelclass C(B) where class B(A) — a chain
HierarchicalMultiple children inherit from the same parent
Multipleclass D(A, B) — child inherits from more than one parent
HybridA combination of the above

Multiple inheritance & MRO (Method Resolution Order)

When multiple parents define the same method, Python decides which one wins using MRO, computed via the C3 linearization algorithm. You can always inspect it with ClassName.__mro__ or ClassName.mro().

python
class A:
    def greet(self):
        return "Hello from A"

class B(A):
    def greet(self):
        return "Hello from B"

class C(A):
    def greet(self):
        return "Hello from C"

class D(B, C):   # the classic "diamond problem"
    pass

d = D()
print(d.greet())          # Hello from B  -> left-to-right, depth-first, but C3-linearized
print(D.__mro__)
# (D, B, C, A, object)  -> B is checked before C, C before A
🎤 Diamond problem explained simply

If B and C both inherit from A, and D inherits from both B and C, which version of a method does D get if both B and C override it? Python resolves this deterministically via MRO (D → B → C → A → object), unlike languages such as C++ where it can be ambiguous.

8. Polymorphism

"Many forms" — the same method name/interface behaves differently depending on the object calling it. In Python this shows up in three main flavors:

a) Method Overriding (runtime polymorphism)

python
class Shape:
    def area(self):
        raise NotImplementedError

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14 * self.r ** 2

class Square(Shape):
    def __init__(self, s): self.s = s
    def area(self): return self.s ** 2

for shape in [Circle(2), Square(3)]:
    print(shape.area())     # calls the correct .area() for each type automatically

b) Duck Typing

Python doesn't check types before calling a method — "if it walks like a duck and quacks like a duck, it's a duck." Any object with the right method can be used, regardless of inheritance.

python
class Duck:
    def sound(self): return "Quack"

class Human:
    def sound(self): return "I'm quacking!"

def make_it_sound(entity):
    print(entity.sound())   # no type checking, just calls .sound()

make_it_sound(Duck())    # Quack
make_it_sound(Human())   # I'm quacking!

c) Operator Overloading

Give built-in operators (+, ==, <...) custom meaning for your own classes via dunder methods.

python
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"

v1, v2 = Vector(1, 2), Vector(3, 4)
print(v1 + v2)     # Vector(4, 6) -> "+" now works on Vector objects

9. Abstraction

Abstraction hides how something is done and exposes only what it does. In Python this is formalized with the abc module — an Abstract Base Class (ABC) defines a contract that subclasses must fulfill.

python
from abc import ABC, abstractmethod

class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount):
        pass          # no implementation -> subclasses MUST override this

    def receipt(self):   # concrete method -> shared by all subclasses
        return "Thank you for your payment!"

class CreditCard(PaymentMethod):
    def pay(self, amount):
        return f"Paid {amount} using Credit Card"

class UPI(PaymentMethod):
    def pay(self, amount):
        return f"Paid {amount} using UPI"

# PaymentMethod()        # TypeError: Can't instantiate abstract class
cc = CreditCard()
print(cc.pay(500))       # Paid 500 using Credit Card
print(cc.receipt())      # Thank you for your payment!
💡 Why this matters for LLD

Abstract classes/interfaces are how you satisfy the Open/Closed Principle and enable Strategy / Factory patterns — e.g. a PaymentStrategy interface lets you plug in new payment types without touching existing checkout code. Expect to define at least one ABC in almost every LLD round.

10. Dunder (Magic) Methods Cheat Sheet

These let your custom objects integrate naturally with Python's built-in syntax and functions.

MethodTriggered byPurpose
__init__ClassName(...)Initialize a new instance
__repr__repr(obj), console echoUnambiguous, dev-facing representation
__str__str(obj), print(obj)Readable, user-facing representation
__eq__obj1 == obj2Custom equality logic
__lt__obj1 < obj2Enables sorting / comparisons
__len__len(obj)Custom length behavior
__getitem__obj[key]Indexing / slicing support
__iter__for x in objMakes an object iterable
__call__obj(...)Makes an instance callable like a function
__enter__/__exit__with obj as x:Context manager protocol
python
class Book:
    def __init__(self, title, pages):
        self.title, self.pages = title, pages

    def __repr__(self):
        return f"Book('{self.title}', {self.pages})"   # for debugging

    def __str__(self):
        return f"{self.title} ({self.pages} pages)"     # for humans

    def __eq__(self, other):
        return self.pages == other.pages

    def __lt__(self, other):
        return self.pages < other.pages

b1 = Book("Clean Code", 464)
b2 = Book("The Hobbit", 310)

print(b1)                     # Clean Code (464 pages)   -> __str__
print([b1, b2])                # [Book('Clean Code', 464), Book('The Hobbit', 310)] -> __repr__
print(b1 == b2)                # False -> __eq__
print(sorted([b1, b2]))        # sorted by pages using __lt__
⚠️ __eq__ without __hash__

Defining __eq__ automatically sets __hash__ to None, making instances unhashable (can't be used in a set or as a dict key). Define __hash__ explicitly if you need both.

11. Composition vs Inheritance

Composition models a "has-a" relationship by holding a reference to another object, instead of extending it. The well-known guideline: "favor composition over inheritance" — it keeps classes more loosely coupled and flexible.

python
# Inheritance -> "is-a": tightly coupled to parent's implementation
class Engine:
    def start(self):
        return "Engine starting..."

# Composition -> "has-a": Car HAS an Engine, doesn't extend it
class Car:
    def __init__(self):
        self.engine = Engine()      # composed, not inherited

    def start(self):
        return self.engine.start()

car = Car()
print(car.start())   # Engine starting...
# Swapping engines (e.g. ElectricEngine) requires zero change to Car's class hierarchy
InheritanceComposition
Relationshipis-ahas-a
CouplingTight (child depends on parent internals)Loose (depends only on interface)
FlexibilityFixed at compile/class-definition timeCan swap components at runtime
When to useClear taxonomy, shared behavior truly universalAlmost always preferred in LLD answers

📌 Quick Revision — Cheat Sheet

  • 4 Pillars: Encapsulation, Abstraction, Inheritance, Polymorphism
  • self = current instance, passed automatically to instance methods
  • Class var shared across instances; instance var unique per object
  • @classmethod → alternate constructors / class-level state (cls)
  • @staticmethod → utility function, no self/cls needed
  • Encapsulation: _protected (convention), __private (name-mangled), @property for controlled access
  • Inheritance: is-a relationship; super() calls parent; MRO resolves diamond problem
  • Polymorphism: method overriding, duck typing, operator overloading (dunder methods)
  • Abstraction: ABC + @abstractmethod define a contract subclasses must implement
  • Composition > Inheritance in most real LLD designs — favor "has-a" for flexibility

12. Common Interview Questions

🎤 Q: Difference between overloading and overriding?

Overriding = child redefines a parent's method (runtime, needs inheritance). Python has no true method overloading (same name, different signatures) like Java — the last-defined method simply wins. Simulate it with default args, *args/**kwargs, or functools.singledispatch.

python
class Calculator:
    def add(self, a, b, c=0):   # simulate overloading with a default arg
        return a + b + c

calc = Calculator()
print(calc.add(2, 3))       # 5   -> "two-argument" version
print(calc.add(2, 3, 4))    # 9   -> "three-argument" version
# Only ONE method is ever defined -> this is overloading simulation, not real overriding.
🎤 Q: Can you instantiate an abstract class?

No — Python raises TypeError if any @abstractmethod is left unimplemented. This is enforced by the ABCMeta metaclass that ABC uses under the hood.

🎤 Q: Is Python "truly" encapsulated?

No — Python favors "we're all consenting adults" and uses naming conventions (_, __) rather than compiler-enforced access modifiers like private in Java/C++. __private is only name-mangled, not hidden.

🎤 Q: What's the difference between __new__ and __init__?

__new__ is a static method that actually creates and returns the new object (allocates memory); __init__ then initializes its attributes. __new__ is rarely overridden except for singletons or immutable types (like subclassing tuple/str).

🎤 Q: Why favor composition over inheritance?

Deep inheritance hierarchies become fragile ("fragile base class" problem) and tightly couple subclasses to parent implementation details. Composition lets you change behavior at runtime by swapping out the composed object, and avoids forcing an "is-a" relationship where a "has-a"/"uses-a" one is more accurate.
