Creational Design Patterns

Patterns that deal with how objects get created — Singleton, Factory Method, Abstract Factory, Builder, and Prototype — each with a real-world LLD example.

🏗 Design Patterns ⏱ ~25 min read 🎯 GoF Creational family
💡 Why this matters

Every one of these patterns exists to answer the same question: "how do we create objects flexibly, without hard-coding ClassName() everywhere?" This directly supports the Open/Closed Principle — new object types get added without touching the code that creates them.

Overview

1Singleton

Intent: Ensure a class has only one instance for the entire application lifetime, and provide one global access point to it.

Real-world LLD example: A logging service, a database connection pool, or an app-wide configuration manager — you never want two independent instances silently tracking different state.

❌ Naive approach
python
class Logger:
    def __init__(self):
        self.logs = []
    def log(self, msg):
        self.logs.append(msg)

logger1 = Logger()
logger2 = Logger()          # a totally separate instance!
logger1.log("User logged in")
print(len(logger2.logs))    # 0 -> logger2 has no idea logger1 exists
✅ Singleton via __new__
python
class Logger:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.logs = []
        return cls._instance

    def log(self, msg):
        self.logs.append(msg)

logger1 = Logger()
logger2 = Logger()
logger1.log("User logged in")
print(logger1 is logger2)     # True -> same object
print(len(logger2.logs))      # 1    -> shared state, as intended

The Pythonic way is usually simpler — a module is already a singleton, since Python caches imports:

python
# logger_instance.py
class _Logger:
    def __init__(self):
        self.logs = []
    def log(self, msg):
        self.logs.append(msg)

logger = _Logger()     # created once, on first import

# anywhere else:
# from logger_instance import logger
# logger.log("...")   -> always the same shared object
🚨 Singleton is a controversial pattern

It introduces global mutable state, makes unit testing harder (state leaks between tests), and hides a class's dependencies. Many interviewers consider it an anti-pattern and expect you to justify it (e.g. "I'd only use this for a config/logger, and I'd still make it injectable for tests"). Also, a naive Singleton is not thread-safe — two threads can race past the if cls._instance is None check simultaneously; production code needs a lock around instance creation.

2Factory Method

Intent: Define a method for creating an object, but let the decision of which concrete class to instantiate be made at runtime (based on input, config, etc.) — the calling code never calls a concrete constructor directly.

Real-world LLD example: A notification system that sends Email, SMS, or Push notifications depending on user preference — exactly the kind of thing that grows new types over time.

python
from abc import ABC, abstractmethod

class Notification(ABC):
    @abstractmethod
    def send(self, message): pass

class EmailNotification(Notification):
    def send(self, message): print(f"Email: {message}")

class SMSNotification(Notification):
    def send(self, message): print(f"SMS: {message}")

class PushNotification(Notification):
    def send(self, message): print(f"Push: {message}")

class NotificationFactory:
    @staticmethod
    def create(channel: str) -> Notification:
        mapping = {
            "email": EmailNotification,
            "sms": SMSNotification,
            "push": PushNotification,
        }
        if channel not in mapping:
            raise ValueError(f"Unknown channel: {channel}")
        return mapping[channel]()     # caller never calls EmailNotification() directly

notifier = NotificationFactory.create("sms")
notifier.send("Your OTP is 4242")     # SMS: Your OTP is 4242

# Adding WhatsAppNotification later only means editing the factory's mapping,
# never the calling code that requests notifications.
🎤 Interview one-liner

Factory Method is the concrete mechanism behind the Open/Closed Principle example you saw on the SOLID page — instead of an if/elif chain scattered across the codebase, all "which class do I create" logic lives in exactly one place.

3Abstract Factory

Intent: Produce families of related objects without specifying their concrete classes — used when objects must be created in matching sets that stay consistent with each other.

Real-world LLD example: A cross-platform UI toolkit that must render either an all-Windows set of widgets or an all-Mac set — you should never accidentally get a Windows button paired with a Mac checkbox.

python
from abc import ABC, abstractmethod

# --- Abstract product interfaces ---
class Button(ABC):
    @abstractmethod
    def render(self): pass

class Checkbox(ABC):
    @abstractmethod
    def render(self): pass

# --- Windows family ---
class WindowsButton(Button):
    def render(self): return "[Windows Button]"

class WindowsCheckbox(Checkbox):
    def render(self): return "[Windows Checkbox]"

# --- Mac family ---
class MacButton(Button):
    def render(self): return "(Mac Button)"

class MacCheckbox(Checkbox):
    def render(self): return "(Mac Checkbox)"

# --- Abstract Factory ---
class UIFactory(ABC):
    @abstractmethod
    def create_button(self) -> Button: pass
    @abstractmethod
    def create_checkbox(self) -> Checkbox: pass

class WindowsFactory(UIFactory):
    def create_button(self): return WindowsButton()
    def create_checkbox(self): return WindowsCheckbox()

class MacFactory(UIFactory):
    def create_button(self): return MacButton()
    def create_checkbox(self): return MacCheckbox()

def render_ui(factory: UIFactory):
    print(factory.create_button().render())
    print(factory.create_checkbox().render())

render_ui(WindowsFactory())   # [Windows Button] / [Windows Checkbox] -> never mixed
render_ui(MacFactory())       # (Mac Button) / (Mac Checkbox)
Factory MethodAbstract Factory
ProducesOne productA family of related products
MechanismOne creation methodAn object with multiple creation methods
ExampleNotificationFactory.create("sms")WindowsFactory creating a matching Button + Checkbox

4Builder

Intent: Separate the construction of a complex object from its final representation, building it up step-by-step — avoids a constructor with a huge number of optional parameters (the "telescoping constructor" problem).

Real-world LLD example: Building a customizable Burger or an HTTP request where most fields are optional and construction reads better as a chain of steps.

❌ Telescoping constructor
python
class Burger:
    def __init__(self, bun, patty, cheese=False, lettuce=False,
                 tomato=False, sauce=None, bacon=False):
        ...

# Caller has to remember every positional slot, even to skip most of them:
b = Burger("sesame", "chicken", False, True, False, "mayo", True)
# Which arg was cheese again? Error-prone and unreadable.
✅ Builder pattern
python
class Burger:
    def __init__(self):
        self.bun = None
        self.patty = None
        self.toppings = []

    def __repr__(self):
        return f"{self.bun} bun, {self.patty} patty, toppings={self.toppings}"

class BurgerBuilder:
    def __init__(self):
        self.burger = Burger()

    def set_bun(self, bun):
        self.burger.bun = bun
        return self                       # return self -> enables chaining

    def set_patty(self, patty):
        self.burger.patty = patty
        return self

    def add_topping(self, topping):
        self.burger.toppings.append(topping)
        return self

    def build(self) -> Burger:
        return self.burger

burger = (
    BurgerBuilder()
    .set_bun("sesame")
    .set_patty("chicken")
    .add_topping("cheese")
    .add_topping("bacon")
    .build()
)
print(burger)    # sesame bun, chicken patty, toppings=['cheese', 'bacon']
# Self-documenting: every step's purpose is explicit, and steps can be optional/reordered.
🎤 When to reach for Builder

Use it when a class has 4+ optional/combinable fields, or when construction genuinely happens in ordered steps (e.g. an HttpRequestBuilder setting URL → headers → body → timeout). If a class only has 2-3 required fields, a plain constructor is simpler — don't over-engineer.

5Prototype

Intent: Create a new object by cloning an existing instance instead of building one from scratch — useful when construction is expensive, or you want many variations of a similar base object.

Real-world LLD example: A game with a "default enemy" template that gets cloned and slightly modified per spawn, instead of re-running expensive setup logic each time.

python
import copy

class Enemy:
    def __init__(self, kind, health, weapons):
        self.kind = kind
        self.health = health
        self.weapons = weapons          # a mutable list -> needs a deep copy

    def clone(self):
        return copy.deepcopy(self)      # Prototype: clone instead of rebuild

    def __repr__(self):
        return f"{self.kind}(hp={self.health}, weapons={self.weapons})"

goblin_template = Enemy("Goblin", health=50, weapons=["dagger"])

goblin1 = goblin_template.clone()
goblin2 = goblin_template.clone()
goblin2.weapons.append("shield")        # only affects goblin2

print(goblin1)   # Goblin(hp=50, weapons=['dagger'])
print(goblin2)   # Goblin(hp=50, weapons=['dagger', 'shield'])
print(goblin1 is goblin2)   # False -> independent objects, no shared references
⚠️ Shallow vs deep copy

Always check whether copy.copy() (shallow) is enough or you need copy.deepcopy(). A shallow copy duplicates the top-level object but still shares references to nested mutable objects (like weapons above) — mutating the clone's list would silently mutate the original's too.

📌 Quick Revision — Cheat Sheet

  • Singleton — one instance, globally shared. Watch for thread-safety and testability concerns.
  • Factory Method — one method decides which single concrete class to instantiate.
  • Abstract Factory — a factory that produces a whole matching family of related objects.
  • Builder — construct step-by-step via chained calls; fixes the telescoping-constructor problem.
  • Prototype — clone an existing object (copy.deepcopy) instead of rebuilding from scratch.

Common Interview Questions

🎤 Q: Is Singleton an anti-pattern?

It's controversial rather than strictly bad — it introduces global state and hidden dependencies, which hurts testability. Most interviewers accept it for genuinely global, stateless-ish services (logging, config) but expect you to note the trade-off, and ideally still make it injectable (pass the instance in) rather than reaching for the global directly everywhere.

🎤 Q: Factory Method vs Abstract Factory — how do you tell them apart quickly?

Count the products: if you're creating one kind of object whose exact class varies, that's Factory Method. If you're creating a matching set of several different object types that must stay consistent with each other (like a UI theme's button + checkbox + scrollbar), that's Abstract Factory.

🎤 Q: Why not just use keyword arguments with defaults instead of Builder?

For a handful of optional fields, keyword args are simpler and idiomatic Python — Builder is overkill. Reach for Builder when construction has real sequential steps, validation between steps, or so many optional combinations that a single constructor call becomes unreadable regardless of keyword args.

🎤 Q: How would you make the naive Singleton thread-safe?

Wrap the instance-creation check in a threading.Lock, using double-checked locking so the lock is only acquired the first time (checking _instance is None once outside the lock, then again inside it before creating), so subsequent calls don't pay the locking cost.
