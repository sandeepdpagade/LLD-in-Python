BookMyShow (Movie Ticket Booking)

The interview question that's really about one thing: how do you stop two people from booking the same seat at the same time?

🎬 Practice Problem ⏱ ~22 min read 🎯 Concurrency-safe State design
💡 What this problem is really testing

Anyone can model Movie, Theatre, and Seat classes. What separates a strong answer is handling the race condition: two users selecting the same seat within milliseconds of each other. If you don't bring this up unprompted, expect it as a direct follow-up.

1Problem Statement

Design a movie ticket booking system that supports:

  • Browsing shows (a movie playing on a specific screen at a specific time).
  • Selecting one or more seats for a show and holding them temporarily during checkout.
  • Confirming the booking after payment, or releasing the hold if checkout doesn't complete.
  • Guaranteeing a seat is never double-booked, even under concurrent requests.

2Clarifying Requirements

FunctionalNon-functional
Lock selected seats for the duration of checkoutNo two users can ever hold/confirm the same seat
Auto-release a hold if payment isn't completed in timeSeat pricing should vary by seat type without touching booking logic
Confirm booking atomically across multiple selected seatsPartial failures (one seat in a multi-seat request unavailable) must roll back cleanly

3Identifying Core Entities

EntityResponsibility
SeatTracks its own type and status (available/locked/booked) — a small state machine
ShowA movie at a specific time, owning the seat map for that screening
BookingA user's attempt to reserve a set of seats for a show
BookingManagerThe single entry point that locks, confirms, and rolls back bookings

4Design Decisions & Patterns Used

DecisionPatternWhy
A seat moves through AVAILABLE → LOCKED → BOOKED (or back to AVAILABLE)State (via enum + guarded transitions)Makes illegal transitions (booking an already-locked seat) impossible by construction
Each Seat guards its own status flip with a lock—The actual fix for the race condition: the check-then-set has to be atomic per seat
One BookingManager coordinates all bookingsSingletonA single source of truth for what's been booked, building-wide
Locking multiple seats either fully succeeds or fully rolls back—Prevents a user from ending up with 1 of 2 requested seats stuck in limbo

5Implementation

Seat — a small, thread-safe state machine

python
from enum import Enum
import threading
import time

class SeatType(Enum):
    SILVER = 100
    GOLD = 200
    PREMIUM = 350

class SeatStatus(Enum):
    AVAILABLE = "available"
    LOCKED = "locked"
    BOOKED = "booked"

class Seat:
    def __init__(self, seat_id: str, seat_type: SeatType):
        self.seat_id = seat_id
        self.seat_type = seat_type
        self.status = SeatStatus.AVAILABLE
        self.lock_time = None
        self._mutex = threading.Lock()          # guards the check-then-set below

    def try_lock(self) -> bool:
        with self._mutex:                        # atomic: no other thread can interleave here
            if self.status == SeatStatus.AVAILABLE:
                self.status = SeatStatus.LOCKED
                self.lock_time = time.time()
                return True
            return False

    def confirm(self):
        with self._mutex:
            self.status = SeatStatus.BOOKED

    def release(self):
        with self._mutex:
            self.status = SeatStatus.AVAILABLE
            self.lock_time = None
🚨 This is the crux of the whole problem

Without the threading.Lock, two threads could both read status == AVAILABLE as true before either one sets it to LOCKED — both would then believe they'd successfully claimed the seat. The lock makes "check status, then set status" one atomic operation instead of two separate steps a second thread could slip between.

Show & Booking

python
class Show:
    def __init__(self, show_id: str, movie_name: str, seats: list[Seat]):
        self.show_id = show_id
        self.movie_name = movie_name
        self.seats = {s.seat_id: s for s in seats}

class Booking:
    def __init__(self, booking_id: str, show: Show, seat_ids: list[str], user_id: str):
        self.booking_id = booking_id
        self.show = show
        self.seat_ids = seat_ids
        self.user_id = user_id
        self.confirmed = False

BookingManager (Singleton, with rollback)

python
class BookingManager:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self):
        if getattr(self, "_initialized", False):
            return
        self.bookings: dict[str, Booking] = {}
        self._initialized = True

    def hold_seats(self, show: Show, seat_ids: list[str], user_id: str) -> Booking:
        locked = []
        for sid in seat_ids:
            seat = show.seats[sid]
            if seat.try_lock():
                locked.append(seat)
            else:
                for s in locked:                # roll back the partial lock
                    s.release()
                raise Exception(f"Seat {sid} is not available")

        booking_id = f"BKG-{len(self.bookings) + 1}"
        booking = Booking(booking_id, show, seat_ids, user_id)
        self.bookings[booking_id] = booking
        return booking

    def confirm_booking(self, booking: Booking):
        for sid in booking.seat_ids:
            booking.show.seats[sid].confirm()
        booking.confirmed = True
        print(f"Booking {booking.booking_id} confirmed for {booking.user_id}")

    def cancel_hold(self, booking: Booking):
        for sid in booking.seat_ids:
            booking.show.seats[sid].release()
        del self.bookings[booking.booking_id]

Putting it together

python
seats = [Seat(f"A{i}", SeatType.GOLD) for i in range(1, 6)]
show = Show("S1", "Inception", seats)

manager = BookingManager()
booking = manager.hold_seats(show, ["A1", "A2"], user_id="user_42")
manager.confirm_booking(booking)   # Booking BKG-1 confirmed for user_42

# A second user racing for the same seat fails cleanly, no partial state:
try:
    manager.hold_seats(show, ["A1", "A3"], user_id="user_99")
except Exception as e:
    print(e)   # Seat A1 is not available -> A3 is auto-released via rollback, not left locked

6. Extending the Design (common follow-ups)

🎤 "What happens if a user locks seats but never completes payment?"

Add a lock_time-based expiry (already tracked above): a background job periodically scans for seats stuck in LOCKED longer than, say, 5 minutes and calls release() on them. This is the same "TTL cleanup" idea you'd use for any temporary hold.

🎤 "How would seat pricing vary by seat type or day of week?"

Strategy pattern — introduce a PricingStrategy (as in the Parking Lot and Creational Patterns pages) that computes the final price from SeatType and the show's date/time, injected into BookingManager without changing its booking logic at all.

🎤 "Why lock per-seat instead of one global lock for the whole show?"

A global lock would serialize all bookings for a show, even ones for completely different seats — a huge throughput bottleneck for a popular showtime. Per-seat locks only create contention when two people genuinely want the same seat, which is the only case that actually needs to be serialized.

📌 Quick Revision — Cheat Sheet

  • Entities: Seat, Show, Booking, BookingManager.
  • State: AVAILABLE → LOCKED → BOOKED, guarded transitions prevent illegal states.
  • The core fix: a per-seat threading.Lock around "check then set," not a global lock.
  • Atomicity: multi-seat holds either fully succeed or fully roll back — no seat left stuck in limbo.
  • Classic follow-ups: lock timeout/expiry, dynamic pricing (Strategy), per-seat vs global locking trade-off.
